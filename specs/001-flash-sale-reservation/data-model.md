# Data Model: Flash Sale Inventory Reservation System

**Date**: 2026-05-22
**Spec**: [spec.md](./spec.md)
**Plan**: [plan.md](./plan.md)

Two tables in 3NF. No denormalized stock counter. Available stock is always a query, never
a column. The schema enforces every invariant it can with `CHECK`, `NOT NULL`, and `FK`
constraints so that application bugs cannot silently corrupt inventory state.

---

## Entities

### `sales`

A flash sale event. Capacity is set at creation and immutable for the sale's lifetime.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | `uuid` | `PRIMARY KEY` | UUIDv4, generated by the server. |
| `name` | `text` | `NOT NULL`, `CHECK (length(name) BETWEEN 1 AND 200)` | Human-readable label. |
| `total_capacity` | `integer` | `NOT NULL`, `CHECK (total_capacity > 0)` | Immutable for the sale's lifetime. |
| `created_at` | `timestamptz` | `NOT NULL`, default `now()` | Audit. |

**Relationships**: has many `reservations` (FK `reservations.sale_id`).

**Locking role**: The sales row is the serialization anchor for every reservation-create
transaction. The reservation create flow takes `FOR NO KEY UPDATE` (not plain `FOR
UPDATE`) on this row — see `reservations.create` flow below for rationale.

---

### `reservations`

A hold on N units of a sale, owned by a session. Active until either manually released or
TTL-expired; terminal records are kept as tombstones (no hard delete).

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | `uuid` | `PRIMARY KEY` | UUIDv4. |
| `sale_id` | `uuid` | `NOT NULL`, `REFERENCES sales(id) ON DELETE RESTRICT` | A sale's reservations cannot be orphaned. |
| `session_id` | `text` | `NOT NULL`, `CHECK (length(session_id) BETWEEN 1 AND 128)` | Anonymous session/token identifier. |
| `quantity` | `integer` | `NOT NULL`, `CHECK (quantity > 0)` | Always positive. |
| `created_at` | `timestamptz` | `NOT NULL`, default `now()` | Server time. |
| `expires_at` | `timestamptz` | `NOT NULL` | Set to `created_at + interval '60 seconds'` at insert time. |
| `released_at` | `timestamptz` | `NULL` allowed | Set when manually released; mutually exclusive with `expired_at`. |
| `expired_at` | `timestamptz` | `NULL` allowed | Set when TTL-expired; mutually exclusive with `released_at`. |
| `status` | `reservation_status` (enum) | `NOT NULL` | `'active' | 'released' | 'expired'`. |

**Enum**:

```sql
CREATE TYPE reservation_status AS ENUM ('active', 'released', 'expired');
```

**Table-level constraints**:

```sql
-- Status and terminal timestamps must agree.
CHECK (
  (status = 'active'   AND released_at IS NULL AND expired_at IS NULL) OR
  (status = 'released' AND released_at IS NOT NULL AND expired_at IS NULL) OR
  (status = 'expired'  AND released_at IS NULL AND expired_at IS NOT NULL)
)

-- expires_at must be after created_at.
CHECK (expires_at > created_at)
```

**Indexes**:

```sql
-- Used by inventory view (sum active by sale).
CREATE INDEX reservations_sale_active_idx
  ON reservations (sale_id) WHERE status = 'active';

-- Used by the TTL expirer worker.
CREATE INDEX reservations_active_expiring_idx
  ON reservations (expires_at) WHERE status = 'active';

-- Optional: look up a user's reservations.
CREATE INDEX reservations_session_idx
  ON reservations (session_id);
```

### `idempotency_records`

Backs the `Idempotency-Key` header on `POST /api/sales/{sale_id}/reservations`. One row
per (session, key) pair. The cached response (status code + body) is replayed verbatim on
repeat requests with the same key and a matching request body. The same row also serves as
a row-level lock that serializes concurrent requests sharing one key.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `idempotency_key` | `text` | `NOT NULL`, `CHECK (length(idempotency_key) BETWEEN 1 AND 128)` | Client-supplied. |
| `session_id` | `text` | `NOT NULL` | The submitting session's identifier (scopes the key per-session). |
| `sale_id` | `uuid` | `NOT NULL`, `REFERENCES sales(id) ON DELETE CASCADE` | The sale targeted by the original request. |
| `request_hash` | `bytea` | `NOT NULL` | SHA-256 of the canonical request body (`{"quantity": N}`) plus the `sale_id`. |
| `response_status` | `smallint` | `NOT NULL`, `CHECK (response_status BETWEEN 100 AND 599)` | HTTP status code returned to the original caller. |
| `response_body` | `jsonb` | `NOT NULL` | Verbatim response payload returned to the original caller. |
| `reservation_id` | `uuid` | `NULL` allowed, `REFERENCES reservations(id) ON DELETE SET NULL` | Set when the original request succeeded; useful for auditing the original → cached-response linkage. |
| `created_at` | `timestamptz` | `NOT NULL`, default `now()` | Used by the garbage-collection sweep. |

**Primary key**: `(idempotency_key, session_id)` — the natural scope for replay matching.

**Indexes**:

```sql
-- Garbage collection sweep: drop records older than the 24h retention window.
CREATE INDEX idempotency_records_gc_idx
  ON idempotency_records (created_at);
```

**Retention**: A background sweep deletes rows older than 24 hours; after deletion,
a request using the same key behaves as a fresh request (no replay protection). The sweep
runs in the same backend process as the TTL expirer (see `expirer/`), on a longer
interval (e.g., every 60 seconds).

**Why a separate table (not a column on `reservations`)**:
- Rejected requests (e.g., `INSUFFICIENT_STOCK`) must also be idempotent — but they
  never produce a `reservations` row, so a column there could not store their cached
  response.
- The lock that serializes concurrent same-key requests must be acquirable before any
  reservation row exists, ruling out reservation-row-based locking.

## Derived view: inventory state

`Available` is not a column. The inventory read endpoint computes it inside a single
query so the answer is consistent with the current `reservations` table state.

```sql
SELECT
  s.id AS sale_id,
  s.total_capacity,
  COALESCE(SUM(r.quantity) FILTER (WHERE r.status = 'active'), 0) AS currently_reserved,
  s.total_capacity
    - COALESCE(SUM(r.quantity) FILTER (WHERE r.status = 'active'), 0) AS available_to_reserve
FROM sales s
LEFT JOIN reservations r ON r.sale_id = s.id
WHERE s.id = $1
GROUP BY s.id;
```

For dashboard reads we do **not** take any lock — the read is "current-best-effort" and
acceptable up to a 1-second freshness budget (SC-003). Authoritative reads happen inside
the create-reservation transaction and are protected by `FOR UPDATE` on `sales`.

## State machine: `reservations.status`

```
                  manual release
            ┌──────────────────────────┐
            │                          ▼
        active ───── TTL ─────►  expired (terminal)
            │                          ▲
            │                          │ no transition;
            ▼                          │ release wins if it commits
        released (terminal)            │
            (no further transitions)
```

- **Initial state**: `active` (set by `reservations.create`).
- **Terminal states**: `released`, `expired`. No transitions out.
- **Race**: A concurrent manual-release and TTL-expirer transaction both try to claim the
  same `active` reservation. Each transaction locks the reservation row with `FOR UPDATE`,
  re-checks `status = 'active'` inside the lock, and exits as a no-op if it lost the race.

## Transaction flows

### `reservations.create` (the consistency-critical path)

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';

-- (a) Serialize against the sale.
SELECT id, total_capacity
  FROM sales
 WHERE id = $1
   FOR NO KEY UPDATE;   -- ← Principle II: pessimistic row lock.
-- Why FOR NO KEY UPDATE rather than FOR UPDATE: child INSERTs (e.g. into
-- idempotency_records, which carries an FK to sales.id) implicitly take
-- FOR KEY SHARE on the parent row. FOR UPDATE would conflict with that and
-- collapse concurrent throughput; FOR NO KEY UPDATE serializes our reservation
-- writers against each other while leaving the FK-validation lane open.
-- If 0 rows: SALE_NOT_FOUND. If lock_timeout: LOCK_TIMEOUT.

-- (b) Compute current reserved inside the lock.
SELECT COALESCE(SUM(quantity), 0)
  FROM reservations
 WHERE sale_id = $1 AND status = 'active';

-- (c) If total_capacity - reserved >= requested_qty, proceed; else ROLLBACK with
--     INSUFFICIENT_STOCK (return current available count to the caller for UX).
INSERT INTO reservations
  (id, sale_id, session_id, quantity, created_at, expires_at, status)
VALUES
  ($new_id, $1, $session, $qty, now(), now() + interval '60 seconds', 'active');

COMMIT;
```

### `reservations.create` with `Idempotency-Key`

When the request carries an `Idempotency-Key` header, the create flow wraps the
transaction above with an idempotency check. The whole thing remains a single
transaction so the reservation insert and the idempotency record commit atomically.

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';

-- (i) Attempt to claim the (key, session) slot. ON CONFLICT DO NOTHING + RETURNING
--     gives us a clean race-winner / race-loser branch.
INSERT INTO idempotency_records
  (idempotency_key, session_id, sale_id, request_hash,
   response_status, response_body, reservation_id)
VALUES
  ($key, $session, $sale, $request_hash,
   0, '{}'::jsonb, NULL)              -- placeholder; overwritten before commit.
ON CONFLICT (idempotency_key, session_id) DO NOTHING
RETURNING idempotency_key;

-- Two branches:

-- Branch A: RETURNING produced a row → we won the race. Run (a)–(c) from the
--           plain create flow above. Then:
UPDATE idempotency_records
   SET request_hash    = $request_hash,
       response_status = $final_status,
       response_body   = $final_body,
       reservation_id  = $reservation_id   -- NULL on rejected requests
 WHERE idempotency_key = $key AND session_id = $session;

-- Branch B: RETURNING produced no rows → another request holds the slot.
--           SELECT ... FOR UPDATE blocks until that transaction commits/rolls back.
SELECT request_hash, response_status, response_body, reservation_id
  FROM idempotency_records
 WHERE idempotency_key = $key AND session_id = $session
   FOR UPDATE;
-- Now compare request_hash to ours:
--   * match     → return cached (response_status, response_body) verbatim; do not
--                 touch sales / reservations.
--   * mismatch  → ROLLBACK and return IDEMPOTENCY_KEY_MISMATCH (HTTP 422), including
--                 the original and submitted hashes in the error details.

COMMIT;
```

**Notes on this flow**:
- The `INSERT ... ON CONFLICT DO NOTHING RETURNING` is the canonical PostgreSQL pattern
  for "claim-or-observe" against a unique key.
- In Branch B, the `SELECT ... FOR UPDATE` waits on the winner's row lock; once the
  winner commits, the loser reads the now-populated `response_status` / `response_body`
  and replays them. If the winner rolled back (e.g., `INSUFFICIENT_STOCK`), the row is
  gone — the loser then retries Branch A on the next request iteration. (In practice
  the application code wraps Branches A/B in a small `for` loop with a bounded retry
  count, all inside the same lock-timeout budget.)
- The `request_hash` is computed in application code as
  `SHA-256(sale_id || canonical_json({"quantity": N}))`. Path parameters are included
  so cross-sale collisions cannot match.
- The `reservation_id` foreign key uses `ON DELETE SET NULL` so that tombstoned
  reservations can still be retained while the idempotency record's cached response
  remains intact.

### `reservations.release` (manual)

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';

SELECT id, sale_id, session_id, status
  FROM reservations
 WHERE id = $1
   FOR UPDATE;

-- If 0 rows: RESERVATION_NOT_FOUND (graceful 200/204 to client per FR-014).
-- If status != 'active': RESERVATION_TERMINAL (graceful 200/204; no inventory change).
-- If session_id != caller's session: RESERVATION_NOT_FOUND (do not leak existence).

UPDATE reservations
   SET status = 'released', released_at = now()
 WHERE id = $1;

COMMIT;
```

### `reservations.expire` (background worker, per row)

```sql
BEGIN;
SET LOCAL lock_timeout = '2s';

SELECT id, status
  FROM reservations
 WHERE id = $1
   FOR UPDATE;

-- If status != 'active': no-op (release won the race).
UPDATE reservations
   SET status = 'expired', expired_at = now()
 WHERE id = $1 AND status = 'active';

COMMIT;
```

The worker selects candidates with:

```sql
SELECT id FROM reservations
 WHERE status = 'active' AND expires_at <= now()
 ORDER BY expires_at
 LIMIT 100;
```

and processes each in its own transaction (no batch update — keeps the per-row lock window
tight and avoids interfering with concurrent create transactions on the parent sale).

## Migrations

`backend/migrations/` will hold versioned, append-only SQL files in `golang-migrate`
format:

```
backend/migrations/
├── 0001_init.up.sql            # CREATE TYPE, CREATE TABLE sales, CREATE TABLE reservations,
│                               # all CHECK constraints, indexes.
├── 0001_init.down.sql          # DROP TABLE / DROP TYPE (local resets only).
├── 0002_idempotency.up.sql     # CREATE TABLE idempotency_records + indexes.
└── 0002_idempotency.down.sql   # DROP TABLE idempotency_records.
```

Forward-only in CI; down-migrations exist purely for local development convenience and
are not required to be runnable in production.
